Combining Microphysics and Observers¶

This page assumes you’ve read the conceptual introduction to monoids in Monoids and the note on C++ concepts in Programming Guide. Here we go one level more concrete: what MicrophysicalProcess and Observer actually require, how the >> operator combines them, and a fully worked, annotated example of each.

Microphysics and Observers as Software Abstractions¶

Physically, a “microphysical process” is something that changes droplets — e.g. condensation/evaporation or collision-coalescence. Physically, an “observer” is something that observes the state of a simulation — e.g. writing out super-droplet radii. As software abstractions in Cleo, both are C++20 concepts: named sets of requirements on a type, checked by the compiler during compilation. Microphysical processes and Observers are entirely independent of each other, they only share the same basic idea in that they are defined as monoids and thus are arbitrarily combinable with themselves.

The MicrophysicalProcess concept (libs/superdrops/microphysicalprocess.hpp):

template <typename P>
concept MicrophysicalProcess =
    requires(P p, const TeamMember& tm, const unsigned int t, subviewd_supers supers,
             State& state, const NullSDMMonitor mo) {
      { p.next_step(t) } -> std::convertible_to<unsigned int>;
      { p.on_step(t) } -> std::same_as<bool>;
      { p.run_step(tm, t, supers, state, mo) } -> std::same_as<subviewd_supers>;
    };

These requirements define if a type is a valid MicrophysicalProcess: any type with these three functions is a microphysical process — regardless of what physics it implements. next_step says when it next wants to run; on_step says whether the current timestep is one of those times; run_step actually mutates the super-droplets in one gridbox’s State and returns the view of super-droplets (possibly resized, e.g. after the edge-case where the coalescence of two superdroplets with multiplicity of 1 creates a super-droplet of multiplicity 0). The requirements that make up the concept of a MicrophysicalProcess ensure that any type that is a microphysical process will fit into the (sub-)timestepping routines in RunCleo and SDMMethods, as depicted in Timestepping.

The Observer concept (libs/observers/observers.hpp) is structurally similar but larger, because an observer also needs one-time before/after timestepping entry points:

template <typename Obs>
concept Observer = requires(Obs obs, unsigned int t, const viewd_constgbx d_gbxs,
                            const subviewd_constsupers d_supers) {
  { obs.next_obs(t) } -> std::convertible_to<unsigned int>;
  { obs.on_step(t) } -> std::same_as<bool>;
  { obs.before_timestepping(d_gbxs, d_supers) } -> std::same_as<void>;
  { obs.after_timestepping() } -> std::same_as<void>;
  { obs.at_start_step(t, d_gbxs, d_supers) } -> std::same_as<void>;
  { obs.get_sdmmonitor() };
};

before_timestepping/after_timestepping run once, at the very start/end of a run (e.g. to write fixed metadata). at_start_step is where an observer may do its observing/writing, called once per outer-loop timestep (see Understanding and Adapting main.cpp). get_sdmmonitor() returns an SDMMonitor — a separate, smaller concept (see libs/superdrops/sdmmonitor.hpp) for a sub-component of observers that need to record something during the microphysics sub-timestepping itself (e.g. how much mass condensed or precipitated), rather than only at the start of a step; if an observer doesn’t need this it returns NullSDMMonitor{}.

How Combination Works: the Monoid Machinery¶

Both concepts have an associated “combined” struct and an operator>> overload. For microphysics (microphysicalprocess.hpp):

template <MicrophysicalProcess Microphys1, MicrophysicalProcess Microphys2>
struct CombinedMicrophysicalProcess {
 private:
  Microphys1 a;
  Microphys2 b;

 public:
  CombinedMicrophysicalProcess(const Microphys1 a, const Microphys2 b) : a(a), b(b) {}

  unsigned int next_step(const unsigned int subt) const {
    return Kokkos::min(a.next_step(subt), b.next_step(subt));   // whichever wants to run sooner
  }

  bool on_step(const unsigned int subt) const { return a.on_step(subt) || b.on_step(subt); }

  subviewd_supers run_step(const TeamMember& team_member, const unsigned int subt,
                            subviewd_supers supers, State& state, const SDMMonitor auto mo) const {
    supers = a.run_step(team_member, subt, supers, state, mo);   // a acts first, on a's output
    supers = b.run_step(team_member, subt, supers, state, mo);   // then b acts on a's result
    return supers;
  }
};

auto operator>>(const MicrophysicalProcess auto a, const MicrophysicalProcess auto b) {
  return CombinedMicrophysicalProcess(a, b);
}

CombinedMicrophysicalProcess itself satisfies the MicrophysicalProcess concept (it has next_step/on_step/run_step with the right signatures) — which is precisely what makes it a monoid: combining two members of the set produces another member of the same set, so you can chain arbitrarily many together (a >> b >> c combines left-to-right). Note the order matters for run_step: a >> b means a runs, then b runs on a’s result — not that they run simultaneously or in some unspecified order. For this reason it makes sense to combine “fast” processes (e.g. condensation) before “slow” ones (e.g. collision-coalescence).

The final property of the monoid for microphysical processes, that of the null element which does nothing under combination with another microphysical processes (see Monoids), is fulfilled by the NullMicrophysicalProcess struct. Itss on_step always returns false, its next_step returns the largest possible integer, and its run_step is a no-op.

Observer follows exactly the same notions as the MicrophysicalProcess explained above, with CombinedObserver and its operator>> overload. This is however one extra piece: combining two observers also combines their SDMMonitor``s via ``CombinedSDMMonitor, so that get_sdmmonitor() of the combined observer returns a monitor that runs both constituent monitors - in escence allowing monitors to act as monoids nested inside observers. (Both observers and monitors also have their own null elements, NullObserver and NullSDMMonitor.)

Worked Example: Combining Two Microphysical Processes¶

This is (lightly trimmed) real code from examples/rainshaft1d/src/main_rshaft1d.cpp:

inline MicrophysicalProcess auto create_microphysics(const Config& config,
                                                     const Timesteps& tsteps) {
  // (1) condensation/evaporation, with its own constant sub-timestep
  const auto c = config.get_condensation();
  const MicrophysicalProcess auto cond =
      Condensation(tsteps.get_condstep(), &step2dimlesstime, c.do_alter_thermo, c.maxniters,
                   c.rtol, c.atol, c.MINSUBTSTEP, &realtime2dimless);

  // (2) collision-coalescence, with Long's hydrodynamic collision efficiency, and its own
  //     (in general different) constant sub-timestep
  const PairProbability auto coalprob =
      LongHydroProb(config.get_coalescence().constcoaleff.coaleff);
  const MicrophysicalProcess auto colls =
      CollCoal(tsteps.get_collstep(), &step2realtime, coalprob);

  // (3) combine: condensation acts on the super-droplets first, then collision-coalescence
  //     acts on condensation's result, each on its own adaptive sub-timestep
  return cond >> colls;
}

Line by line:

  1. Condensation is constructed with its own sub-timestep (tsteps.get_condstep()) and solver tolerances read from the YAML config (see Tutorial: Creating a New Cleo Experiment From Scratch). It satisfies MicrophysicalProcess by construction (its class implements the three required functions).

  2. LongHydroProb satisfies a different, narrower concept, PairProbability (the probability that a randomly-sampled pair of super-droplets collides), which CollCoal takes as one of its constructor arguments; CollCoal itself is what satisfies MicrophysicalProcess.

  3. cond >> colls produces a single CombinedMicrophysicalProcess<Condensation, CollCoal> value. Its exact C++ type is long and you never need to write it out — this is exactly what the MicrophysicalProcess auto return-type syntax allows (see Cleo’s Code Structure’s note on concepts). At runtime, on every sub-timestep of the combined process, condensation runs on whatever sub-timestep multiple it should, and collision-coalescence runs on whatever (in general different) sub-timestep multiple it should — each governed independently by its own next_step/on_step.

Worked Example: Combining Observers¶

Also from main_rshaft1d.cpp, combining several observers, including a helper function that itself builds one observer out of several smaller “data-collector” pieces:

template <typename Dataset, typename Store>
inline Observer auto create_superdrops_observer(const unsigned int interval, Dataset& dataset,
                                                Store& store, const int maxchunk) {
  // each of these collects one super-droplet attribute into the output dataset
  CollectDataForDataset<Dataset> auto sdid       = CollectSdId(dataset, maxchunk);
  CollectDataForDataset<Dataset> auto sdgbxindex = CollectSdgbxindex(dataset, maxchunk);
  CollectDataForDataset<Dataset> auto xi         = CollectXi(dataset, maxchunk);
  CollectDataForDataset<Dataset> auto radius     = CollectRadius(dataset, maxchunk);
  CollectDataForDataset<Dataset> auto msol       = CollectMsol(dataset, maxchunk);
  CollectDataForDataset<Dataset> auto coord3     = CollectCoord3(dataset, maxchunk);

  // combined into one "collect everything" object, then wrapped in an Observer
  const auto collect_sddata = coord3 >> msol >> radius >> xi >> sdgbxindex >> sdid;
  return SuperdropsObserver(interval, dataset, store, maxchunk, collect_sddata);
}

template <typename Dataset, typename Store>
inline Observer auto create_observer(const Config& config, const Timesteps& tsteps,
                                     Dataset& dataset, Store& store) {
  const auto obsstep  = tsteps.get_obsstep();
  const auto maxchunk = config.get_maxchunk();
  const auto ngbxs    = config.get_ngbxs();

  const Observer auto obs0 = StreamOutObserver(obsstep * 10, &step2realtime);       // progress to stdout
  const Observer auto obs1 = TimeObserver(obsstep, dataset, store, maxchunk, &step2dimlesstime);
  const Observer auto obs2 = GbxindexObserver(dataset, store, maxchunk, ngbxs);
  const Observer auto obs3 = NsupersObserver(obsstep, dataset, maxchunk, ngbxs);
  const Observer auto obs4 = MassMomentsObserver(obsstep, dataset, store, maxchunk, ngbxs);
  const Observer auto obssd = create_superdrops_observer(obsstep, dataset, store, maxchunk);

  return obssd >> obs4 >> obs3 >> obs2 >> obs1 >> obs0;
}

There are two levels of combination happening here. In create_superdrops_observer, CollectDataForDataset is another monoid (i.e. is a set with a null element in which the set is defined by a concept as well as an associated class which can combine types satisfy that concept into a new type which also satisfies the concept). The create_superdrops_observer function combines several CollectDataForDataset types, each of which collects data for a different superdroplet attribute, into a single CollectDataForDataset type: coord3 >> msol >> radius >> xi etc., and then returns a SuperdropsObserver observer which wraps that combined collector in functions which output the superdroplet attribute data to a Zarr dataset and satisfy the full Observer concept. That resulting Observer type is then itself combined with five other independent observers (StreamOutObserver, TimeObserver, GbxindexObserver, etc.) via the >> overload for observers (analogous to the one you saw for microphysics above) to create the single Observer type which is returned from create_observer and used in the simulation.

Tip

For observers, order matters for readability even when it doesn’t change results: it’s usual in Cleo’s examples to build the “innermost”/most specific observer or process first, as done here in the create_superdrops_observer function, and then combine outward, as shown above, so the final return statement reads as a short summary of everything being combined.

Compatibility Rules and Constraints¶

  • You can only combine two values that satisfy the same concept — you cannot >> a MicrophysicalProcess with an Observer; there is a separate operator>> overload (and a separate Combined... struct) defined for each monoid, and the C++ compiler will reject a call whose argument types don’t match any overload’s constraints.

  • Order is significant for the effect of combination (as noted above for microphysics), even though it doesn’t matter for which sub-timestep the combination runs on (next_step and on_step use min/logical-or). Monoids are commutative but not associative!

  • An empty/no-op branch of a combination should use the monoid’s null member (NullMicrophysicalProcess{}, NullObserver{}) rather than, say, an if statement guarding whether to call create_microphysics at all — this keeps the type of your SDM fixed at compile time regardless of runtime configuration choices, which is the whole point of the monoid pattern (B2026a [Bayley et al., 2026], Sect. 2.3).

  • Because combination happens via templates, the type of your combined microphysics/observer is fixed once you write your main.cpp and compile — you cannot pick a different combination at runtime from the YAML config file alone (though you can, and generally should, use the YAML config to set the parameters of each already-selected process — see Tutorial: Creating a New Cleo Experiment From Scratch).
